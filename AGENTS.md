# AGENTS.md

Operating notes for an agent working in `redrob-labs/redrob-query`. Everything here was read
from the tree or measured against the live repository, not assumed.

## What this repository is

Redrob Query is a JVM-free desktop database client for PostgreSQL, MySQL, SQLite, and MongoDB,
built as a Tauri 2 shell around a React 19 front end and a Rust core crate. Version 0.1 ships a
read-only desktop workspace: mutation commands are not registered with Tauri at all, so
"read-only" is enforced by the absence of an IPC command rather than by a runtime check. The same
front end also runs in a plain browser against deterministic in-memory fixtures, which is how the
product demos without a database or anyone's credentials.

The workflow is informed by DBeaver Community, but there is no DBeaver, Eclipse, OSGi, JDBC, or
Java code here. Keep it that way: user-visible strings name Redrob Query.

## Layout

| Path | What lives there |
| --- | --- |
| `src/` | The React 19 front end, 26 files. `components/` holds the panels (Navigator, QueryEditor, ResultGrid, AiPanel, CommandPalette), `store/` holds the Zustand workspace store and its localStorage persistence, `api/bridge.ts` is the single seam between the UI and either Tauri IPC or the browser DemoBridge, `domain/types.ts` is the shared type surface, `test/setup.ts` is the vitest jsdom setup. |
| `crates/redrob-core/` | The Rust core: `connection.rs`, `query.rs`, `profile_store.rs`, `secret.rs`, `ai.rs`, `models.rs`, `error.rs`. SQLx drives PostgreSQL/MySQL/SQLite, the `mongodb` crate drives Mongo, `reqwest` with rustls carries AI traffic. `publish = false`. |
| `src-tauri/` | The desktop shell. `src/commands.rs` holds 11 `#[tauri::command]` functions and `src/lib.rs` registers exactly those 11 in `generate_handler!`. `capabilities/default.json` grants only `core:default` to the `main` window. |
| `src-tauri/gen/schemas/` | Tauri-generated ACL and capability schemas, four JSON files, and they are committed. Do not hand-edit them; they are regenerated by the Tauri build. |
| `scripts/` | Four Node ESM scripts: `validate-release.mjs` (the release-metadata validator wired to `npm run release:check`), `prepare-release-config.mjs`, `release-matrix.mjs`, `rewrite-updater-urls.mjs`. |
| `docs/` | `ARCHITECTURE.md`, `SECURITY.md`, `DEMO.md`, `DBEAVER-PORTING-MAP.md`. |
| `dist/`, `target/`, `node_modules/` | Build output and dependencies, all three ignored by `.gitignore` and untracked. `git ls-files dist` returns nothing even though the directory exists locally. |

Documentation is bilingual: `README.md` and `CONTRIBUTING.md` have `.ko.md` siblings. Change both
or neither.

## Toolchain and commands

Node with npm is the JavaScript package manager, pinned by `"packageManager": "npm@11.4.2"` with
`engines` requiring Node >= 22.12.0 and npm >= 11.0.0. Rust comes from rustup, and
`rust-toolchain.toml` pins channel `1.94.0` with `clippy` and `rustfmt`. The Cargo workspace root is
the repository root, not `src-tauri`; its members are `crates/redrob-core` and `src-tauri`. Install
JavaScript dependencies with `npm ci`, never `npm install`, so the lockfile decides.

Commands run and their exit codes, on this checkout at `origin/develop` (`8c1dbb5`):

| Command | Exit code | Note |
| --- | --- | --- |
| `npm run release:check` | 0 | 0.12s. Printed "Release metadata is synchronized for Redrob Query 0.1.0." |
| `npm run typecheck` | 0 | `tsc --noEmit -p tsconfig.app.json`. |
| `npm test` | 0 | vitest, 4 files, 74 tests passed, 11.8s. |
| `npm run build` | 0 | Runs typecheck then `vite build`, 1.5s. |
| `npm run rust:fmt` | 127 | `cargo: not found`. No rustup, cargo, or rustc on this host, so nothing Rust was verified locally. |

`npm run check` is the whole gate in one command: `release:check`, `test`, `build`, `rust:fmt`,
`rust:clippy`, `rust:test`. Run it before asking for review. If Rust is not installed, say so in the
pull request rather than implying the Rust half passed.

Three connector tests in `redrob-core` are `#[ignore]` and need live databases. Cargo does not read
`.env`, so export the URLs from `.env.example` in your shell and run
`cargo test --locked -p redrob-core --all-features -- --ignored`. Skipping them is normal; claiming
they passed without exporting the URLs is not.

## Branch model and gitflow

`develop` is the default branch and the base of every pull request. Of the two open right now, this
one targets `develop` and #18 (`release/v0.1.0`) targets `main`, which is what a release promotion
should do. `main` is released state and moves
only by merging `develop` (through a `release/*` or `hotfix/*` branch) into it. Release tags are cut
from `main`.

A hotfix branches from `main`, merges into `main`, releases, and THEN `main` is merged back into
`develop`. That last step is the one people drop, and dropping it is a real failure: the sibling
repository redrob-code spent a month with a lockfile its own default branch could not install from
because the back-merge never happened. Check the current state before you trust it:

```bash
git rev-list --count origin/develop..origin/main   # commits on main that develop lacks
git rev-list --count origin/main..origin/develop   # commits on develop that main lacks
```

Both printed `0` when this file was written, so the two branches were identical and nothing was
owed in either direction. A nonzero first number means a release or hotfix has not been merged back
into `develop` and every branch cut from `develop` is missing it.

One part of the convention is machine-checked: the release workflow fetches `origin/main` and fails
the tag unless `git merge-base --is-ancestor "$GITHUB_SHA" origin/main` holds, so tagging straight
off `develop` fails instead of shipping. Which branch a pull request comes FROM is not checkable by
a ruleset, so "only `release/*` and `hotfix/*` merge into `main`" rests on reviewers.

Working branches are `<type>/<slug>` off `develop`, types `feat`, `fix`, `chore`, `docs`, `test`,
`refactor`, `perf`. Merges are squash-only and the branch is deleted, so the squash body is the
pull request body.

## Protection, and what is actually enforced

Both `develop` and `main` are protected the same way, read from the branch-protection API:

- pull requests only, no direct pushes;
- force pushes blocked, deletion blocked;
- `required_approving_review_count` is 0, so a pull request can merge with no review;
- `enforce_admins` is off, so an admin is not bound by any of the above;
- `required_status_checks.contexts` and `.checks` are both EMPTY.

That last line is the one to internalize. CI does run: `.github/workflows/ci.yml` fires on
`pull_request` and on pushes to `main` and `develop`, and pull request #17 shows all three jobs
passing (Release metadata/types/tests/build, Format/clippy/tests, Rust security advisories). But
because protection requires zero checks, a red run blocks nothing. Merge is a human decision every
time, and with 0 required reviews and admin enforcement off, a broken pull request can reach
`develop` with nothing standing in the way. Read the checks yourself before merging; do not wait
for GitHub to stop you.

`CONTRIBUTING.md` says both CI jobs "are required before a merge". That is not what protection
says, and the workflow now has three jobs, not two. Trust the API over the prose.

The CI workflow is deliberately `pull_request`, never `pull_request_target`, and consumes no
secrets, so a fork's pull request gets an identical run with no credential. Do not "fix" that by
switching the trigger.

## What an agent gets wrong first

- **`npm run release:check` is a real gate, not a formality.** `scripts/validate-release.mjs`
  asserts the version is identical across `package.json`, the Cargo workspace, `tauri.conf.json`,
  and both `package-lock.json` version fields; that `rust-version` in `Cargo.toml` matches the
  `rust-toolchain.toml` channel; that `productName` is `Redrob Query` and the identifier is
  `ai.redrob.query`; that the window label is `main` and `devUrl` is `http://127.0.0.1:1420`. Bump
  a version in one file and this fails.
- **Every icon in `src-tauri/icons` must be RGBA.** The validator reads byte 25 of each PNG (the
  IHDR colour type) and demands 6, because `tauri::generate_context!` panics at COMPILE TIME on a
  non-RGBA icon. One RGB PNG means the desktop app cannot be built at all, and that shipped once.
- **Adding a Tauri command is a security change.** The read-only guarantee is that no mutation
  command exists in the 11 registered in `src-tauri/src/lib.rs`. Registering one silently removes
  the guarantee the README states.
- **GitHub Actions are SHA-pinned** in both workflows and updated by Dependabot's
  `github-actions` ecosystem. Keep the `# vX.Y.Z` comment next to the SHA when you touch one.
- **`unsafe_code = "forbid"`** at the workspace level, with clippy `all` and `pedantic` warned.
  CI runs clippy with `-D warnings`, so a pedantic lint fails the build.
- **`src-tauri/tauri.release.conf.json` is gitignored on purpose**: it is generated inside a
  release runner by `scripts/prepare-release-config.mjs`. Do not create it locally and commit it.
- **Do not commit anything from `.env`.** `.env.example` is the only env file tracked, and secrets
  in the desktop app live in the OS keyring.
